## Part 1: what changed and how to set it up

### Upstox market data (5 or 30 levels)

- **Setting:** `broker.data: upstox` in `config/system.yaml`.
- **What Upstox offers:** its V3 feed has `full` mode (5 depth levels) and `full_d30` (30 levels). `full_d30` needs **Upstox Plus**, covers NSE equity only, and allows 50 instruments **per connection** by Upstox's Websocket Plus announcement (5 connections: 250), but **per user** by an Upstox staff answer. Part 1.5 explains how nsealgo handles both. There is no 20-level mode.
- **How nsealgo uses it:** it streams your chosen stocks in `full_d30` and everything else in `full`:

  ```yaml
  upstox: {..., depth: {mode: full_d30, symbols: [RELIANCE, HDFCBANK, ICICIBANK, ...]}}   # max 50
  ```

- **In code:** every quote now carries `bids` and `asks` (price, qty), best first.
- **Recordings:** they keep `feeds.record_depth` levels (default 5). 30 levels × 50 stocks runs to roughly a gigabyte a day, so raise it only when you need 30-level replays.

### Shoonya orders from your static IP (dormant since 3.7: Fyers places the orders)

Since 3.7, `broker.orders` chooses the order broker, and Fyers gets the same static-IP proxy and fail-closed check described below (`brokers.fyers.proxy` / `static_ip`). Shoonya ships with `orders: false`.

StaticIP.in delivers your dedicated IP as an HTTP/HTTPS proxy.

**Setup:**
1. Register that IP with Shoonya (API settings), then put it in `.env`:
   ```
   STATICIP_PROXY=http://USER:PASSWORD@HOST:PORT
   STATIC_IP=203.0.113.7
   ```
2. `nsealgo netcheck shoonya` shows the IP your requests leave from and whether it matches. It also reports the latency of a new connection against a kept-alive one on *your* line.
3. Set `broker.execution: shoonya` to trade live.

**What runs automatically:**
- **Static-IP check first:** before any login or order, nsealgo asks an IP-echo service *through the proxy*. If the answer isn't `static_ip`, the Shoonya login is refused and nothing trades (fail closed).
- **What is proxied:** only Shoonya's REST calls. The Upstox feed connects directly, since market data needs no static IP and a proxy would only add delay.
- **Environment variables ignored:** system-wide `HTTP(S)_PROXY` variables are ignored for order traffic, so routing is always explicit.

### Lower order latency

The Shoonya SDK used a fresh `requests.post` for every call, with **no timeout**. nsealgo now replaces it with a pooled connection:
- **Warm connection:** DNS, TCP, TLS and the proxy tunnel are set up at login, and kept warm with a ping every 45 s. Orders reuse the open, encrypted connection.
- **Socket options:** `TCP_NODELAY` and `SO_KEEPALIVE` are set on every socket, including proxied ones.
- **Timeouts:** 3 s to connect and 10 s to read, on every call.
- **No automatic retries:** a retried order could be a duplicate.
- **Latency stats:** per endpoint (`transport.stats()`).

The saving is the handshake round trips on every order; `netcheck` measures it on your connection. The proxy adds one hop: pick a StaticIP.in location near Mumbai.

## Part 1.5: deeper books for more stocks (Upstox, since 3.6)

| Source | Depth | Instruments | Notes |
|---|---|---|---|
| Fyers TBT | 50 levels, with order counts | 3 connections × 5 = 15 | from Fyers' API docs (Part 4) |
| Upstox `full_d30` (Upstox Plus) | 30 levels | 50 per connection × up to 5 connections = **250**, or **50** in all | NSE equity; see the limit below |

**Upstox's limit, as documented:**

- **Websocket Plus announcement:** 30-level mode allows up to 50 instruments **per websocket connection**, with up to 5 connections per user.
- **V3 feed docs:** the limits table says only "Full D30: 50 instrument keys".
- **Upstox staff answer** in Upstox's community: the 50 is a **hard limit per user**, across connections. The user who asked reported that only the first connection received data.

**How nsealgo handles it:** `feeds.depth_overlay.source: upstox` opens up to 5 websockets of 50 stocks each in `full_d30`.
- If a connection receives nothing for `verify_seconds` (60) while another one streams, the per-user limit is in force. That connection is retired, capacity locks to the connections Upstox serves, and the reason is logged.
- Nothing is retired while the market is quiet.
- Your first live session settles which reading is right.

If Upstox is also your main data feed, it already uses one websocket, so the overlay uses at most 4. In that case keep the main feed at `depth.mode: full`, so the two don't compete for 30-level slots.

**Merging and focus:**
- **Upstox as an extra layer, not a second feed:** its book replaces a quote's book only when it is deeper, fresh (under `max_age`, 2 s) and not crossed. Prices, volume and timestamps still come from your main feed.
- **Focus, every `depth_focus_seconds` (60 s):** the engine ranks open positions first, then each intraday strategy's candidates in turn. With `source: fyers_tbt,upstox`, TBT takes the top 15 (50 levels) and Upstox the next slice (30 levels).

Dhan's 20-level feed was removed in 3.6. The Dhan broker adapter remains for orders and ordinary data.

## Part 2: the Radeon 8060S (done in 3.3)

### Install on the PX13

1. Install AMD's **"AMD Software: PyTorch on Windows Edition 7.2.1"** graphics driver. AMD's install guide requires driver 26.2.2 for this release.
2. Install **Python 3.12**; AMD's wheels are cp312 only.
3. Run `powershell -ExecutionPolicy Bypass -File scripts\windows\setup.ps1 -Gpu`. It installs the ROCm SDK wheels, then `torch 2.9.1+rocm7.2.1` from `repo.radeon.com`, prints the detected GPU, and runs `nsealgo gpu --fresh`.
4. Run `pytest -q`. On a machine with PyTorch, `test_torch_matches_numpy_on_every_kernel` also runs and compares every kernel on the GPU with NumPy.

### How the choice is made

- **Written once:** each kernel uses a small operations layer with a NumPy version and a PyTorch version (`compute/ops.py`). The NumPy test suite therefore checks the same kernel code the GPU runs.
- **`nsealgo gpu` per kernel and size:**
  * runs a synthetic input on both backends;
  * requires the GPU result to **match NumPy** (float32 tolerance);
  * picks the GPU only if it is **over 10% faster**, transfers included.
- **Caching:** decisions are cached per machine signature (PyTorch, ROCm, GPU name, dtype), so a driver or PyTorch update triggers a new measurement.
- **Run-time errors:** a GPU error sends that kernel back to the CPU for good.
- **Parallel workers:** worker processes always use the CPU, so 16 processes don't fight over one GPU context.
- **Opting out:** `compute.device: cpu` turns the GPU off entirely.

### What runs where

| Kernel | Used by | Expectation on the PX13 |
|---|---|---|
| `fragility`: batched covariance eigenvalues (absorption ratio) and batched Prim minimum spanning trees | fragility overlay timelines in backtests and research | GPU likely for large universes (200–500 stocks); CPU for Nifty 50 |
| `book_features`: microprice, weighted imbalance, depth within ±10/25 bps, pressure | Part 3 signals; research on recorded depth | CPU at live size (hundreds of books); GPU likely for tens of thousands of recorded snapshots |
| `mlofi`: multi-level order-flow imbalance between snapshots | Part 3 signals; research | same as above |

These expectations are guesses until `nsealgo gpu` measures them on your machine.

Batching helped even before any GPU, measured on this project's 1-core test machine with results identical to ~5e-16:

| Fragility timeline, 1,000 sessions | Per-window loop | Batched (CPU) |
|---|---|---|
| 50 stocks | 0.85 s | 0.21 s (4.1×) |
| 200 stocks | 6.74 s | 2.35 s (2.9×) |

The live engine's per-tick work is dominated by Python object handling, not arithmetic, so the GPU won't make live trading faster at today's sizes. Its value is in research and backtests over large universes and recorded depth.

## Part 2 design notes

**Stack:** AMD supports PyTorch **natively on Windows 11** for the Ryzen AI Max+ 395 (gfx1151): PyTorch 2.9.1 on ROCm 7.2.1, Python 3.12, installed with pip from AMD's repository:

```
pip install -f https://repo.radeon.com/rocm/windows/rocm-rel-7.2.1/ "torch==2.9.1+rocm7.2.1"
```

On ROCm, PyTorch exposes the GPU as the `cuda` device, so the code needs no AMD-specific branches. Part 2 will add `setup.ps1 -Gpu`.

What goes to the GPU, and what doesn't:
- **Worth it:** batched maths over many instruments or long histories. Examples: 30-level book analytics for 50 stocks every tick batch, and rolling correlation matrices and eigen-decompositions over 500 stocks × years (market fragility, residual reversion, factor models). These are large, regular array operations.
- **Not worth it:** per-tick logic for one stock. A GPU kernel launch costs microseconds before any maths happens, so for a few hundred numbers the CPU wins. The engine's Python event loop, not arithmetic, is the per-tick cost.
- **How it's decided:** Part 2 adds a compute backend that times each kernel on CPU (NumPy) and GPU (PyTorch) at your real batch sizes, and uses whichever is faster. Results must match to tolerance, enforced by tests. NumPy remains the fallback, so nothing breaks without a GPU.

### Corrections to the research documents

| Claim | What's actually true | What Part 2 does instead |
|---|---|---|
| `torch.from_numpy()` on shared memory gives a GPU tensor ("zero-copy") | It gives a **CPU** tensor; maths on it runs on the CPU. GPU work needs a device tensor (`.to("cuda")`), which is a separate allocation. Managed memory (`hipMallocManaged`) isn't supported on gfx1151 today. | Explicit device tensors, reused buffers and batched transfers, measured on your machine. |
| Lock-free ring buffer via `multiprocessing.Value` | `Value()` wraps a **lock** by default. The sketch also has no overrun detection when the writer laps the reader, and the wrap-around slice is left as "logic here". | If a second process proves worthwhile: a single-producer ring with sequence numbers, overrun counts and a correct wrap-around, tested under load. |
| Pinned memory "vastly speeds up" transfers | It helps across PCIe on discrete GPUs. On this APU CPU and GPU share LPDDR5X, so the benefit is small; the same doc's warning about pinning too much RAM still applies. | Only small staging buffers are pinned, if measurement shows a gain. |
| `requests.post(..., headers=JSON)` to Shoonya | Noren's API takes form data (`jData=…&jKey=…`), not a JSON body. | Part 1 keeps the SDK's exact request format and changes only the transport. |
| "Disable Nagle with TCP_NODELAY" | Correct, and `requests`/urllib3 and aiohttp already set it; nsealgo sets it explicitly anyway, proxied sockets included. | Done in Part 1. |
| OFI over 20 levels, 200 stocks | Upstox gives 30 levels for at most 50 stocks (Plus); the rest get 5. | Part 3 computes multi-level OFI over whatever depth each stock has. |
| Rolling pairs / cointegration trading | Holding a pair overnight needs a short leg, and cash shorts are intraday-only. | Not planned (3.0 is stocks only); cointegration maths could still serve research. |

## Part 3: trading on the order book (done in 3.4)

### The signals (`core/book.py`, read with `ctx.book(key)`)

They are computed for every stock that streams depth (Fyers TBT 50, Upstox 30, Fyers or Upstox 5), on every quote batch, through the CPU/GPU compute layer:

| Signal | Meaning |
|---|---|
| `ofi_z` | Multi-level order-flow imbalance: queue growth, cancellation and price moves at every level, weighted by `decay**level` and scaled by displayed depth. Summed over 30 s, and expressed in standard deviations of its own recent history. |
| `imbalance` | Depth-weighted bid-vs-ask size over the first 5 levels, from −1 to +1. |
| `microprice_bps` | Size-weighted fair price minus the mid. |
| `pressure` | Log ratio of bid to ask depth within 10 bps of mid. |
| `absorb_ask` / `absorb_bid` | Volume that traded at the best ask (bid) while that price **held**, divided by the average size shown there over 60 s. Above about 2, far more traded than was ever displayed and the level didn't break: hidden supply (demand), an **iceberg**. |

`ctx.book()` returns nothing for a stock without fresh depth (older than 5 s, or none at all). Every strategy then keeps its previous top-of-book logic, so nothing changes for stocks outside your deep-book coverage.

**Limitation:** Upstox and Fyers send snapshots, not every individual order, so absorption is an estimate. A trade is counted at the ask if the last price reached the previous best ask, and at the bid if it reached the previous best bid.

### What the strategies do with them

| Strategy | Change when deep book is available | Settings |
|---|---|---|
| `orb` | At the breakout, multi-level flow must point the same way, and no iceberg may sit against it (above the high for longs, below the low for shorts). Blocked breakouts are counted in state (`book_blocked`), and each entry records `ofi_z` and `absorb` in its order metadata. | `book_min_ofi_z: 0`, `book_max_absorb: 3` |
| `scalper` | Uses `ofi_z` and depth-weighted imbalance instead of the top-level versions, and won't trade into an iceberg (`absorb_blocked`). The cost gate is unchanged. | `use_book`, `max_absorb: 3` |
| `market_maker` | Shifts its fair price one tick away from an iceberg, so it doesn't sell to a hidden buyer or buy from a hidden seller. The cost floor is unchanged. | `use_book`, `absorb_threshold: 3`, `absorb_skew_ticks: 1` |

### Before trusting any of it: measure

The thresholds come from the literature and from common sense, not from your data. The workflow:

1. **Record depth.** Set `feeds.record_depth: 20` (or 30) for a few sessions.
2. **Run `nsealgo book-study recordings/<day>.jsonl.gz`.** It reports how well each signal predicts the mid move 5, 30 and 60 s ahead, at 1, 5, 10 and 20 levels. If the deep rows don't beat the 1-level rows on your stocks, the extra depth (and the Upstox Plus or Dhan Data subscription) isn't paying for itself.
3. **Forward-test.** Compare ORB's results and `book_blocked` counts against a run with `ofi_confirm: false`, and let the promotion gates decide.


## Part 4: Fyers for the whole universe, TBT for the deepest books (done in 3.5)

### What Fyers actually offers

| Feed | Depth | Coverage | Notes |
|---|---|---|---|
| Fyers data socket (`SymbolUpdate`, `DepthUpdate`) | best bid/ask, or **5 levels** with order counts | **5,000 data subscriptions** on **one** socket per user; quotes plus depth for a stock count as two | every NSE stock with quotes; about 2,500 with 5-level depth |
| Fyers **TBT** (tick-by-tick) | **50 levels** with order counts; a snapshot, then differences | **3 connections per app per user × 5 symbols per connection = 15 symbols**; 50 channels per connection | NFO and NSE equity (equity since 23 Jun 2025); the docs don't state a price |

These numbers come from Fyers' API v3 documentation; page references are in [FYERS_API_NOTES.md](../05-reference/FYERS_API_NOTES.md). So 50-level books for the whole NSE universe aren't available from Fyers: TBT tops out at 15 symbols.

### What nsealgo builds from it

- **The whole universe, all day:**
  ```yaml
  broker:
    data: fyers
    brokers:
      fyers: {..., depth: depth5}   # adds 5 levels (stream capped at 2,500 stocks: 2 subscriptions each)
  feeds:
    watch: all                      # stream all NSE stocks, not just strategy candidates
  ```
  The book signals from Part 3 (flow, imbalance, iceberg detection) are then computed for the whole universe on every update round, as large batches through the CPU/GPU compute layer. That's the kind of workload where the Radeon can win; `nsealgo gpu` shows whether it does on your machine.
- **50-level TBT books for the most important stocks:**
  ```yaml
  feeds:
    depth_overlay: {source: fyers_tbt, tbt_max_symbols: 15}
  ```
  The focus list (open positions first, then candidates) decides which stocks get them, re-ranked every minute.
- **Tiers:** `source: fyers_tbt,upstox` gives the top 15 stocks 50 levels (TBT), the next 250 (or 50, if Upstox's per-user limit applies) get 30 levels (Upstox Plus), and everything else keeps quotes or 5 levels from the Fyers universe stream.

### How the TBT client works

- **Protocol:** taken from Fyers' official SDK (fyers-apiv3 3.1.18):
  * the socket URL comes from Fyers' lookup service, with a fallback address;
  * the `Authorization: appId:accessToken` header the docs mandate is sent on every connection;
  * a text `ping` every 10 s keeps the connection open;
  * up to 3 connections of 5 symbols each (Fyers' documented limits), subscribed on channel 1 and then resumed;
  * replies are decoded with Fyers' own protobuf schema.
- **Building the book:** a full snapshot arrives first; later messages change only the fields they carry, at the level given by each entry's `num` (0–49), as the docs define it. A book is never used before its first snapshot, and never once it's older than `max_age`.
- **Discovering your limit:** if Fyers refuses a request (for example a lower symbol limit on your plan), its message is logged and kept, so you learn the real number.

### Where the 128 GB and the GPU come in

- **Live:** with `watch: all` and 5 levels, the in-memory books are small. The work is computing signals for ~2,500 books per round, which is batched.
- **Research:** `nsealgo book-study recordings/2026-10-*.jsonl.gz` loads many days of whole-universe depth into memory at once and runs the studies as large GPU-eligible batches. A week of universe recordings fits comfortably in 128 GB.

To record depth for this, set `feeds.record_depth: 5` for the universe; TBT stocks record as many levels as you set, up to 50.
